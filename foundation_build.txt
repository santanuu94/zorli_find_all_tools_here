# ZORLI — PRODUCTION FOUNDATION HARDENING & IMAGE-FIRST DEVELOPMENT

## ROLE

You are working on the existing Zorli web application.

Zorli is a modern web utility platform designed to eventually contain many high-quality browser-based tools across multiple categories.

The long-term vision includes:

* Image tools
* PDF tools
* Developer tools
* Text tools
* Calculators
* Converters
* Downloaders
* SEO tools
* Productivity tools
* Privacy tools
* Other useful utilities

However, **we are NOT building all categories now**.

For the current development phase, Zorli must become an **Image-first production platform**.

We will build and release image tools one by one.

The first goal is to make the existing Zorli foundation production-ready, scalable, maintainable, fast, testable, SEO-friendly, and suitable for incremental deployment.

---

# 1. IMPORTANT: DO NOT REBUILD THE PROJECT

The existing Zorli project already has an established architecture and visual identity.

DO NOT:

* rebuild the application from scratch
* replace the existing UI unnecessarily
* change the Zorli brand identity
* redesign the homepage unnecessarily
* replace React with another framework
* replace Vite
* replace Tailwind
* introduce a database without a real requirement
* introduce authentication without a real requirement
* introduce unnecessary backend infrastructure
* create separate applications for individual tools
* create separate repositories for individual tools

Preserve the existing architecture wherever it is sound.

Make targeted improvements.

# 9. CODE SPLITTING AND LAZY LOADING

This is a priority.

The current project has a relatively large production JavaScript bundle.

The application must NOT load every future tool's JavaScript when the user visits the homepage.

Implement route/tool-level lazy loading.

Conceptually:

```text
Homepage
   ↓
Load only core Zorli UI
   ↓
User opens JPG → PNG
   ↓
Load JPG → PNG implementation
```

Not:

```text
Homepage
   ↓
Load every image tool
   ↓
Load every PDF tool
   ↓
Load every developer tool
   ↓
Load every calculator
   ↓
Huge bundle
```

Use React lazy loading and dynamic imports where appropriate.

Example concept:

```typescript
const JpgToPng = lazy(
  () => import('@/features/tools/image/jpg-to-png')
);
```

Do NOT blindly lazy-load tiny shared components.

Prioritize:

* heavy tool implementations
* image processing libraries
* PDF libraries
* conversion libraries
* large dependencies
* future tool families

Keep the initial application shell lightweight.

---

# 10. AVOID HEAVY DEPENDENCIES IN THE INITIAL BUNDLE

Before adding any dependency, ask:

1. Is it genuinely necessary?
2. Is there a browser-native API that can do the job?
3. Can the task be performed client-side?
4. Does the dependency significantly increase bundle size?
5. Can it be dynamically imported only when needed?

Prefer:

```text
Browser APIs
↓
small focused libraries
↓
dynamic import
↓
large libraries only when necessary
```

Do not add libraries merely for convenience.

---

# 11. IMAGE TOOLS SHOULD BE BROWSER-FIRST

The Zorli image tools should preferably process files locally in the user's browser whenever technically practical.

Desired architecture:

```text
User selects image
       ↓
Browser receives File
       ↓
Local processing
       ↓
Result generated
       ↓
User downloads result
```

Avoid uploading user images to a server unless a future tool genuinely requires server-side processing.

Benefits:

* better privacy
* lower infrastructure cost
* faster processing for many tasks
* less backend complexity
* lower bandwidth costs

Do not claim "files never leave your device" unless the implementation actually guarantees it.

* avoid unnecessary dependencies

# 13. WEB WORKER ARCHITECTURE FOR HEAVY IMAGE PROCESSING

Prepare the architecture so computationally expensive image processing can eventually move into Web Workers.

For example:

```text
UI
 ↓
Tool Hook
 ↓
Processing Worker
 ↓
Image Processing Engine
 ↓
Result
```

Do NOT introduce Web Workers unnecessarily for trivial operations.

But create a clean abstraction so future CPU-heavy tools can use workers without rewriting the entire application.

The goal is:

```text
UI thread = responsive
Processing = worker when necessary
```

---

# 14. MEMORY SAFETY FOR IMAGE TOOLS

Image processing can consume significant browser memory.

Prepare utilities for:

* object URL creation
* object URL cleanup
* File validation
* file size limits
* image dimension limits
* error handling
* cleanup after conversion
* cancellation where practical

Every:

```typescript
URL.createObjectURL(...)
```

must have an appropriate:

```typescript
URL.revokeObjectURL(...)
```

lifecycle.

Avoid memory leaks.
